Каждый временный механизм в implementation handoff обязан иметь: transition anchor; actual source path/commit; что работает; чего НЕ доказывает; target owner task; retained/replaced boundary; data/schema migration and rollback; required evidence and owner gate; next concrete step. Не создавать параллельную таблицу TODO/DONE. Если registry ещё не содержит отдельную Companion implementation task, явно say decomposition pending; не считать Q-044 реализацией клиента.
Упрощение допускается только при сохранении target contract. Переход не стирает debt после смены чата; новый агент читает applicable transitions, overlay, actual source и последний handoff. Не объявлять target achieved из наличия папки/fixture/подписи/скриншота.

## Ближайшие vertical slices — в порядке допустимых gates
1. Factory: authenticated user/project→approved bounded plan→durable job→one actual content result→technical + brief QA→cost report→export. Use Q-004 evidence then applicable P1/P2 tasks. No paid run without separate cap; keys outside chat. Manual publish sufficient for first slice.
2. Companion: authenticated device pairing→one approved local folder→deterministic task→checked artifact→server result→stop/revoke/sleep-resume. Transport fixtures first, then staging+real Windows. No purchase/outbound messaging/wallet or browser publishing required.
3. Experience: one proven generic repair/tool from either runtime→sanitised package→other runtime compatibility/evidence review→limited activation→rollback. No auto unrestricted self-modification.
Не параллелить независимые трактовки ядра. Separate branches/worktrees per adapter; core/contracts ownership serial review; pinned versions/common fixtures. Не overwrite чужой diff/task state и не merge main без решения.
